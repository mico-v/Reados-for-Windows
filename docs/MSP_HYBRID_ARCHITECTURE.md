# MSP Hybrid Architecture Specification

Status: authoritative architecture and project-boundary specification.

This document defines the target ReadOS MSP architecture. Component documents may describe a narrower implementation, but they must not contradict the ownership and security rules here.

## 1. Objective

Build one portable MSP command runtime that can be embedded by Windows, Linux, and Android hosts while allowing each platform to provide different filesystem, process, PTY, storage, and sandbox capabilities.

The runtime is not a general-purpose shell or operating-system distribution. It is a deterministic, capability-bounded execution substrate for AI agents.

## 2. Primary Design Decisions

1. The host is the authority. Policy, approval, audit, session state, artifact lifecycle, provider access, and product data remain above the native runtime.
2. Portable semantics are shared. Parsing, expansion, virtual paths, builtin commands, execution results, limits, and FFI contracts must not depend on a host OS.
3. Platform capabilities are explicit. A backend reports `Unsupported` when safe runtime evidence does not exist; compilation is not a capability claim.
4. The virtual workspace is canonical. Model-visible paths are virtual paths and are never host paths.
5. Commands use a hybrid model. Safe virtual-workspace builtins are implemented in-process; mature external tools run through verified runtime providers.
6. Arbitrary shell strings are forbidden. External execution uses validated program identities and argv values, never `sh -c`, `cmd /c`, or PowerShell command text generated by the model.
7. The two native runtime generations must converge. `native/msp-core` is a migration source and compatibility oracle, not the permanent target architecture.

## 4. Ownership Matrix

| Concern | Owner | Must not own |
| --- | --- | --- |
| Product policy and approval | Product host | Native implicit authorization |
| Terminal product audit | Product host | Duplicate native product audit |
| Session/transcript/artifact | Product host | Platform backend persistence rules |
| PDF/chat/provider/workflows | `ReadOS.App` | Portable Rust business logic |
| Command parsing and expansion | Portable Rust runtime | Host filesystem or process access |
| Virtual path contract | Portable Rust backend contract | OS path conversion |
| Builtin command semantics | Portable Rust command packs | Host `PATH`, locale, or shell |
| Host workspace access | Platform workspace backend | Policy or approval decisions |
| External program lifecycle | Platform process/PTY backend | Arbitrary program discovery |
| Runtime bundle identity | Verified runtime provider | Host `PATH` fallback |
| ABI/JNI memory ownership | Adapter/FFI layer | Product behavior |

## 5. Command Lifecycle

Every command attempt follows one lifecycle:

```text
request
→ parse and prepare
→ project bounded execution metadata
→ host policy/approval
→ execute builtin, domain command, or verified external runtime
→ sanitize and bound output
→ terminal result
→ one product audit record
→ transcript/artifact projection
```

Rules:

- The runtime may prepare a command before approval, but must not execute effects before host authorization.
- Parse, unknown-command, policy, cancellation, backend, process, and command failures all produce terminal results.
- Pre-policy failures use a not-evaluated policy state.
- Native evidence may be validated by the host but never creates a second product audit record.
- Cancellation is reported truthfully. Boundary checks are not described as in-flight interruption unless the backend actually terminates the operation.

## 6. Command Taxonomy

### 6.1 Portable virtual-workspace builtins

Implement only commands whose safe subset materially improves agent work over a virtual workspace:

- navigation and bytes: `pwd`, `echo`, `printf`, `cat`;
- listing and metadata: `ls`, `find`, `du`;
- bounded text/byte processing: `head`, `tail`, `wc`, `grep`, selected `sed` behavior;
- small runtime utilities only when their semantics are deterministic and host-free.

These commands:

- operate only on `VirtualPath`, explicit stdin, explicit variables, and a supplied backend;
- are binary-safe;
- have bounded reads, scans, recursion, output, and argument sizes;
- do not inspect host environment, locale, time zone, `PATH`, filesystem, or process state;
- expose a documented safe subset instead of pretending to implement complete GNU/POSIX behavior.

Do not recreate the complete GNU Coreutils, POSIX userland, or Termux package catalog.

### 6.2 Product/domain commands

Commands such as `pdf`, `library`, `chat`, `workflow`, `artifact`, and document editing remain host commands. They call app-owned services through the managed host and are not moved into the portable command pack.

### 6.3 Verified external runtimes

Complex mature tools are integrated through providers:

- Git;
- Python;
- Node;
- platform tool bundles such as Toybox, BusyBox, or selected Termux packages;
- future converters, compilers, and media tools.

A provider must bind an immutable or revalidated program identity, explicit argv, minimal environment, virtual/sandbox cwd, stdin/stdout/stderr limits, timeout, cancellation, process-tree cleanup, and network policy.

Host registration is represented by `MspVerifiedRuntimeProviderCatalog`; it
stores only verified contracts and produces bounded launch plans. Multi-call
providers may declare an immutable argv prefix, so a Toybox profile can expose
`pwd`, `cat`, or `ls -1` without exposing arbitrary Toybox subcommands or a
shell. The catalog does not launch processes or create product audit records.

The model may select a registered command profile. It may not provide an executable path or arbitrary shell script.

The host-neutral H4.1 contract is implemented by
`MspVerifiedRuntimeProviderContractEvaluator`. Registration combines verified
bundle evidence with bundle-relative entry points, executable digests,
projected-workspace mode, bounded limits, mandatory cancellation/process-tree
cleanup, and license/NOTICE provenance. Launch plans carry only profile id,
argv, virtual cwd, and explicit environment values; PATH/loader keys, shell
entry points, host paths, and missing identity evidence fail closed. Platform
backends must revalidate bundle and executable identity immediately before
launch. This layer does not start processes or create product audit records.

### 6.4 Forbidden direct execution

The following are not MSP execution strategies:

- `bash -c <model text>`;
- `sh -c <model text>`;
- `cmd /c <model text>`;
- PowerShell command strings generated by the model;
- unrestricted Termux shell sessions;
- resolving programs from the host `PATH` without verified identity.

## 7. Virtual Workspace Contract

Model-visible paths:

- are absolute slash-separated virtual paths;
- never contain drive letters, UNC forms, device paths, ADS syntax, backslashes, NUL, or traversal;
- never expose host mount roots, caches, package directories, temporary directories, or broker paths;
- hide internal `.msp` state;
- preserve deterministic case and ordering rules defined by the runtime profile.

Backends may be:

- in-memory;
- app callback-backed;
- host directory-backed;
- mixed/mounted composites;
- Android storage/broker-backed.

All backends implement the same virtual contract. Backend errors are stable categories and do not echo host paths or rejected payloads.

## 8. Platform Profiles

### Windows

- Product host: WinUI/.NET.
- Workspace backend: retained-root/final-handle containment; no pathname check-then-reopen design.
- Process backend: verified bundle identity, Windows Job Object cleanup, optional ConPTY for terminal mode.
- Current legacy `msp-core` behavior may be used as migration evidence but must be exposed through the supported adapter.

### Linux

- Workspace backend: owned root descriptor with `openat2`/descriptor-relative operations and no symlink fallback.
- The current Linux workspace slice adds descriptor-relative `renameat2` for file/subtree moves and
  `unlinkat` for regular-file or empty-directory deletion. Recursive delete, trash, directory
  creation, and fallback path reopening remain unsupported; policy, approval, audit, and product
  routing stay in the host.
- Process backend: `native/msp-process-backend` now provides the first verified
  provider lifecycle slice on Linux: explicit host executable binding and
  digest revalidation, minimal cleared environment, virtual-cwd confinement,
  bounded pipes, timeout/cancellation, and process-group cleanup. Namespace,
  seccomp, and cgroup controls remain hardening work; unsupported kernel
  features must fail closed rather than silently downgrade confinement.
- Unsupported kernels fail closed instead of falling back to unsafe canonicalize-and-open behavior.

### Android

- Portable runtime: Rust `cdylib` packaged through JNI/Kotlin AAR.
- Initial workspace: explicit in-memory files, with a first SAF/ContentResolver
  projection adapter in the Android platform layer.
- Product storage: `MspAndroidContentResolverWorkspaceSource` accepts an
  authorized tree `content://` URI, resolves bounded document reads through
  `DocumentsContract`, and projects bytes into the Rust virtual
  `/workspace/...` namespace. URI authorities and document IDs never cross
  into portable requests or diagnostics; provider errors are path-free and
  typed. This remains a projected temporary workspace, not direct Rust access
  to Android storage.
- Android adapter authority is limited to storage lookup, bounded reads,
  cancellation, and lifecycle cleanup. Policy, approval, audit, credentials,
  process, and PTY authority remain in the host.
- External tools: H4.3 now contains a fixed-profile Android Toybox provider
  experiment (`pwd`, `cat`, `ls`) over an app-private projected workspace.
  `AppOwnedBundle` requires a separately packaged, digest-verified artifact;
  the current `/system/bin/toybox` path is instrumentation-only evidence.
  BusyBox remains a later comparison, and Termux is an explicitly rejected
  optional source rather than a portable-core dependency.
- Termux is never a required portable-core dependency and never grants unrestricted shell access.

## 9. Termux Integration Rules

Termux may be used only as an Android external runtime provider.

Required properties:

- explicit user installation or app-owned integration decision;
- exact package/tool allowlist and version evidence;
- argv execution without shell interpolation;
- dedicated sandbox or projected temporary workspace;
- no implicit shared-storage access;
- explicit network policy;
- bounded output, duration, and child processes;
- cleanup and cancellation evidence;
- license and package provenance recorded per bundled component.

The first Android implementation should prefer a projected temporary workspace. A VFS/broker protocol may replace projection only after lifecycle, cancellation, and path-disclosure rules are proven.

## 10. Capability Negotiation

Portable contracts may advertise:

- workspace read/write/usage;
- process;
- PTY;
- event streaming;
- cancellation;
- runtime provider families.

Rules:

- `Supported` requires target-platform runtime evidence.
- Compile-only, package-only, stub, or fake-native tests remain `Unsupported` or `Blocked`.
- A feature flag cannot turn an unsafe implementation into a supported capability.
- Missing optional capability must not silently fall back to a less safe mechanism.

## 11. ABI and Adapter Rules

- Use owned, versioned, length-delimited values.
- Preserve embedded NUL and non-UTF-8 bytes.
- Every native allocation has one allocator-compatible free path.
- Dispose/invoke races are serialized or rejected safely.
- Request and response limits are operation-specific and enforced before allocation where possible.
- Exceptions and diagnostics omit stack paths, build paths, host roots, provider responses, and secrets.
- Android and .NET adapters project the same portable runtime semantics without taking policy authority.

## 12. Legacy Runtime Convergence

`native/msp-core` currently contains working Windows functionality not yet present in the modular crates. Migration follows these rules:

1. Freeze new general-purpose features in the legacy core. Only security, compatibility, packaging, and migration-enabling fixes are allowed.
2. Inventory every legacy capability as `port`, `adapt`, `defer`, or `delete`.
3. Move portable semantics into the modular workspace without OS dependencies.
4. Move Windows filesystem/process/PTY behavior into platform backends.
5. Route new product adoption through `msp-command-runtime-ffi` and the supported Hosting adapter.
6. Keep differential tests while both implementations exist.
7. Remove legacy product routing, DLL packaging, crate, FFI, and obsolete documentation only after all retirement gates pass.

No new product feature may depend directly on a legacy raw FFI export.

## 13. Project Rules

- One authoritative document per concern; component docs link back here.
- One portable command behavior implementation; platform code supplies capabilities, not duplicate semantics.
- One product authority for policy and audit.
- Every new command declares effect, capabilities, limits, diagnostics, and test profile.
- Every platform capability includes negative security tests.
- Every external runtime integration includes identity, sandbox, network, cleanup, cancellation, provenance, and package gates.
- Generated outputs stay under `artifacts/` or tool-specific ignored build directories.
- Do not commit private workspace data, credentials, imported documents, raw upstream source packages, or generated releases.
- Status documents record evidence and limitations; they do not infer completion from code volume or compilation.

## 14. Definition of Done

The hybrid architecture is complete when:

- Windows, Linux, and Android use the same portable parser/runtime/command-pack contracts;
- each platform has at least one real workspace backend acceptance path;
- Windows and at least one non-Windows platform have a verified external runtime provider;
- product policy, approval, audit, artifact, and session authority remain in the host;
- the flagship ReadOS workflow uses the supported modular runtime boundary;
- package and conformance gates pass without the legacy native DLL; and
- `native/msp-core` and its obsolete adapters/docs are removed.
