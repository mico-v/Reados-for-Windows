# MSP SDK Development Plan

This document turns `docs/MSP_PLAN.md` into the implementation path for ReadOS.

## Product Direction

ReadOS remains a WinUI/C# reading application. MSP becomes the command runtime
inside the application, not a separate end-user product surface.

The model-facing boundary should stay small:

```text
exec_command({ "cmd": "library list" })
```

Internally, ReadOS owns:

- virtual workspace paths
- command registration
- policy decisions
- audit records
- app-specific PDF and chat commands
- artifacts generated by command execution

## Package Shape

Current repository phase:

```text
src/
  ReadOS.App/        WinUI app and ReadOS host adapters
  ReadOS.Msp/        portable .NET MSP runtime and command SDK
tests/
  ReadOS.Msp.Tests/  parser/runtime/workspace tests
native/
  msp-core/          planned Rust native core package boundary
```

Long-term package target:

```text
msp-core             Rust parser/runtime/policy/audit core
ReadOS.Msp.Native    NuGet package containing native binaries
ReadOS.Msp           C# binding and .NET host adapter APIs
ReadOS.App           WinUI host application
```

## Phase 1: In-Process MSP Runtime

Status: started.

Implemented:

- `MspCommandRequest`
- `MspCommandResult`
- `MspArtifact`
- `MspAuditRecord`
- `MspCommandRegistry`
- `MspRuntime`
- basic command-line parser
- read/write workspace abstraction
- in-memory workspace
- policy interface and allow-all policy
- audit sink interface and in-memory sink
- core commands: `help`, `pwd`, `echo`, `ls`, `cat`
- ReadOS host adapter
- ReadOS virtual workspace
- ReadOS commands: `workspace`, `library`, `pdf`

The first ReadOS virtual paths are:

```text
/
/settings.json
/projects
/projects/{projectId}/info.json
/library
/library/{documentId}.json
/documents
/documents/{documentId}/info.json
/documents/{documentId}/outline.json
/documents/{documentId}/pages/{page}.txt
/documents/{documentId}/conversations/{conversationId}.json
```

## Phase 2: Agent Bridge

Add one app-level bridge method for agent execution:

```text
exec_command({ "cmd": "pdf search current \"transformer\"" })
```

The bridge should return:

- `exitCode`
- `stdout`
- `stderr`
- `artifacts`
- `auditRecords`

ReadOS should show command transcript and evidence in the UI before allowing
write-capable commands.

## Phase 3: Write Commands And Policy

Add policy-aware commands:

- `page-label set`
- `outline add`
- `outline delete`
- `attach page`
- `attach range`
- `chat ask`
- `artifact write`

All mutating commands should support one of these modes:

- allow immediately
- require confirmation
- deny

## Phase 4: Native SDK Extraction

Once command behavior is stable, move the language-neutral runtime pieces to
`native/msp-core`:

- shell parser
- command request/result JSON protocol
- policy request/decision protocol
- audit record schema
- command registry metadata
- conformance fixture runner

Keep app capabilities in host adapters. The native core should not know about
WinUI, `Windows.Data.Pdf`, `BitmapImage`, local Windows paths, or ReadOS UI
state.

## Near-Term Command Backlog

Read-only:

- `workspace info`
- `library list`
- `pdf inspect current`
- `pdf text current 12 14`
- `pdf search current "query"`
- `cat /documents/{id}/pages/12.txt`

Mutating:

- `page-label set current 12 "iii"`
- `outline add current 42 "Chapter 3" --level 1`
- `attach page current 12`
- `attach range current 12 18`
- `chat ask current "explain attached pages"`
- `artifact write /artifacts/summary.md`

## Validation Rules

Every command added to MSP must have:

- parser coverage when it depends on quoting or argument shape
- runtime coverage for success and failure exit codes
- audit coverage
- policy behavior if it can mutate user state
- at least one ReadOS host integration check if it touches workspace/PDF/chat

## Verification

Run the full MSP verification path from the repository root:

```powershell
.\scripts\verify-msp.ps1
```

The script runs:

- Rust format check, tests, clippy, and release build for `native/msp-core`
- a PowerShell/C# FFI smoke test against `target/release/msp_core.dll`
- .NET MSP unit tests
- full solution build

If `cargo` is installed in `%USERPROFILE%\.cargo\bin` but the current shell PATH
has not refreshed yet, the script will still find it.
